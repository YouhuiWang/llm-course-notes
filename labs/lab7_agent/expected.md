# Lab 7 预期结果

## 主表

```
环境：8 个文件、3 个任务，每个配置跑 24 次

配置                 成功率   平均步数   平均 token   工具调用
baseline              96%     5.7       2333       9.9
去反思                 67%     5.6       2262       9.2
去记忆                 75%     8.5       4663      14.8
去并行                 96%    11.4       5016      10.8
小模型（错误率 0.35）      83%     6.2       2618      10.0
```

数值会随 `RUNS` 与随机种子轻微波动，但**趋势必须一致**：

| 对比 | 应当观察到 |
|---|---|
| baseline vs 去反思 | 成功率明显下降（≥ 20 个点） |
| baseline vs 去记忆 | 步数与 token 明显上升（≥ 1.4 倍） |
| baseline vs 去并行 | 步数翻倍，成功率不变 |
| baseline vs 小模型 | 成功率下降 10–20 个点 |

## 逐项解读

### 去反思：67%

失败模式是**死循环**：出错后 `policy.last_failed` 被原样返回，状态不变，于是反复踩同一个坑，直到 `stuck >= 4` 触发终止。

如果看到 100%，说明 `use_reflection` 没有真正生效（检查 `act` 里的 `last_failed` 分支）。

### 去记忆：75%，步数 8.5

两个效应叠加：

1. 只看最近 6 条历史 → 反复读已读文件（步数涨 50%）；
2. 到第 8 步"猜"自己读完了 → 信息不全就作答（成功率降 21 个点）。

**这是本实验最值得玩味的一组**：没有记忆不是"慢一点"，而是"不知道自己做没做完"。

### 去并行：96%，步数 11.4

成功率完全不变，步数正好翻倍（8 个文件，一次读 1 个 vs 一次读 3 个）。

**结论**：并行是纯效率优化，不改变正确性。但步数翻倍意味着 token 翻倍——成本是真实的。

### 小模型：83%

错误率 0.15 → 0.35，成功率 96% → 83%。

单步可靠性的差距被 6 步任务放大，符合 $p^n$ 的规律（第 17 讲）。

## 常见失败与排查

| 现象 | 原因 |
|---|---|
| 所有配置数值相同 | `Config` 的字段没传进 `run_agent` |
| 去反思也是 100% | `last_failed` 没被设置，或反思分支没生效 |
| 去记忆也是 100% | `visible` 窗口太大，等于有记忆 |
| 全部 0% | 终止条件写错，`finish` 永远不触发 |
| 步数全是 20 | 无进展检测没生效，全靠 max_steps 兜底 |

## 通过标准

五组配置都打印出完整一行，且满足：

- baseline 成功率 ≥ 90%
- 去反思比 baseline 低 ≥ 15 个点
- 去记忆的 token 比 baseline 高 ≥ 30%
- 去并行的步数约等于 baseline 的 2 倍
