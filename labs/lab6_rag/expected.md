跑通 `main.py` 应该看到下面的表格。**数值不必完全一致**（SVD 有随机性），但趋势应当吻合。

语料 8 篇 → 切成 18 块

配置                 上下文精度     上下文召回       忠实度     答案相关性
--------------------------------------------------------------
BM25 单路            0.542     0.750     0.875     0.388

## 怎么读这张表

| 现象 | 解释 |
|---|---|
| 向量 > BM25（精度与召回都略高） | 查询是自然语言，语义匹配占优 |
| 混合 = 向量 | RRF 的 k=60 压平了头部差距，两路又高度重合 |
| 重排没有提升 | 玩具重排器信号弱于检索本身 |
| BM25 的忠实度 0.875 | 有一次检索不置信，生成器"编"了一句 |
| 答案相关性 0.3–0.4 | 抽取式答案只覆盖了金标文档的部分词 |

## 逐条结果

```
  注意力为什么要除以根号 d          命中 2/3   金标 attention
  MoE 的路由塌缩是怎么回事         命中 2/3   金标 moe
  128K 上下文的 KV cache 有多大 命中 2/3   金标 kv
  量化到 4 bit 有什么代价        命中 2/3   金标 quant
  RAG 的切分块多大合适           命中 2/3   金标 rag
  agent 的误差为什么会累积        命中 1/3   金标 agent
  参数和数据应该怎么配比            命中 1/3   金标 scaling
  外推到更长序列为什么失效           命中 2/3   金标 rope
```

**命中 1/3 的两条**值得单独看：

- "agent 的误差为什么会累积"——"累积"与"误差"两个词在 scaling 文档里也出现（讲 loss 累积），产生混淆；
- "参数和数据应该怎么配比"——"配比"只在 scaling 文档里，但"参数""数据"到处都是。

**这正是 RAG 的真实困难**：通用词造成的假匹配。对策是重排、或者用更好的嵌入模型。

## 常见失败与排查

| 现象 | 原因 |
|---|---|
| 所有配置数值完全相同 | 检索函数没被真正调用，或 top_k 太大 |
| 答案相关性恒为 0 | 金标查询词没取到（检查 `evaluate` 里的 doc_id 遍历） |
| 忠实度恒为 1.0 | 生成器没有"编造"分支，或阈值设得太松 |
| 出现 ZeroDivisionError | 语料太短，某块为空 |

## 通过标准

四组配置都打印出完整一行，且满足：

- 上下文召回在 0.7–0.85 之间（太低说明检索坏了，太高说明任务太简单）
- 忠实度 ≤ 1.0（必须能看到"编造"被指标抓到至少一次）
- 混合配置的召回 ≥ BM25 单路
