# Lab 3 预期结果

## 主表

```
语料：949 字符，401 个预分词单元

词表  250｜合并   36 次｜token 数   660｜每 token 1.27 字符｜无损 ✓
词表  350｜合并  136 次｜token 数   515｜每 token 1.63 字符｜无损 ✓
词表  450｜合并  236 次｜token 数   415｜每 token 2.02 字符｜无损 ✓
```

## 怎么读

| 现象 | 解释 |
|---|---|
| 词表 250 时 token 数 660 > 预分词 401 | 英文单词被拆成字符，token 变多 |
| 词表 450 时 token 数 415 ≈ 预分词 401 | 大部分词已被合并成单个 token |
| 每 token 字符数 1.27 → 2.02 | 词表越大，压缩越强 |
| 无损全是 ✓ | 编码-解码可逆 |

**关键**：token 数不是越少越好。词表越大，模型要学的输出层越大（$|V|\times d$），存在权衡。

## 前 10 条合并规则

```
 1. 'e' + 'n' -> 'en'
 2. 't' + 'h' -> 'th'
 3. 'e' + 'r' -> 'er'
 4. 'i' + 'o' -> 'io'
 ...
```

**规律**：最先被合并的永远是高频字母组合（英语里的 `th`、`en`、`er`），而不是完整单词——因为字母对的频次远高于整词。

## 与 tiktoken 的对照

```
对照 tiktoken（cl100k）：444 token，本实现 565 token
```

差 27%。原因：语料只有 949 字符、预分词更粗、没有 byte-level 回退。

**这不说明实现错了**——真实 tokenizer 在万亿 token 上训练，词表 10 万，自然更高效。

## 常见失败与排查

| 现象 | 原因 |
|---|---|
| 无损 ✗ | `_merge` 没处理重叠对（`aaa` 里的 `aa`） |
| 词表涨不上去 | 语料太小，所有词都合并成单符号了 |
| 编码结果全是单字 | `rank` 排序反了，或 merges 没传给 encode |
| 中文几乎不合并 | 预分词按字切，跨字合并不被允许 |

## 通过标准

三组词表都有输出，且满足：

- 无损全是 ✓
- 词表越大，token 数越少（单调）
- 每 token 字符数随词表增大而上升
